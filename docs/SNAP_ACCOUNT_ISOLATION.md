# Snap sender account isolation

A background camera job captures its Firebase Auth UID and account epoch before it starts. Its upload path, verified sender profile, optimistic message key, confirmation, retry and progress display remain attached to that session. Changing accounts or logging out and back into the same account invalidates the old live job. A stale completion cannot populate the new account's message cache or start a later delivery stage. The editor stays open if its account changed before dispatch; the immediate camera toast describes preparation rather than claiming delivery.

Online jobs verify `profiles/{senderId}.user_id` through a fresh Firestore server read before resolving conversations or uploading media. Image compression, cover generation, conversation creation and story publication check the captured guard around their asynchronous boundaries. Stories use the verified original profile rather than resolving whichever profile is current later. The DM core receives the same guard and deterministic destination-specific message ID. Existing server authentication, membership and storage rules still authorize each request.

Offline queue records have `schemaVersion: 2`, `ownerUid` and the original `senderId`. They retain the original draft, media, unresolved recipients and caption. Another account's queued records are skipped without changing their status or attempts; they do not block that account's later jobs. A restored job must match the active Auth UID and pass fresh profile-ownership verification before any upload or delivery. A recorded-owner draft can restore into a newly verified session for that same owner after a reload or account return. This constructs a new guarded job: the previous live job and all its late callbacks remain invalid.

Older local queue entries lack trustworthy owner bindings. They remain unsent and are marked failed instead of adopting the current account or guessing that a profile ID is an Auth UID. There is no automatic migration of those media blobs. The user must deliberately recapture/resend an unverifiable draft. Failed expired cleanup only touches the current recorded owner's jobs. The queue remains local device storage; this does not add encryption or a multi-device draft service.

The DM transport also sends the captured `expectedSenderUid`. The updated `sendDmMessage` callable rejects a mismatch with its authenticated caller before rate-limit/database work, closing an account switch during SDK token selection. This requires a coordinated, selective callable/client rollout; client guards alone are not that server guarantee. Client guards cannot recall a request already dispatched with the original owner's authentication before an account change. Such a request may complete; its old job's completion is suppressed in newer sessions. Upload bytes already accepted are not deleted automatically. This pass does not revoke existing media URLs, change membership rules or certify native background delivery. Production/provider delivery was not exercised by these tests.

## Atomic local queue and retry recovery

Queue mutations use `idb-keyval.update`, whose installed implementation reads and writes the queue key in one IndexedDB read/write transaction. Independent tabs can enqueue, patch, remove and acknowledge destinations without replacing an array read before another write. Mutations retain unrelated owners' rows. Read, corruption and commit failures propagate; the UI cannot claim a snap is saved after a storage/quota failure. The first queued media payload is retained on re-enqueue, rather than silently replacing it or resetting receipts. The whole queue remains one local key, so storage capacity and large-queue performance still depend on the browser.

Each delivery claims a revision and random token for ten minutes. Competing tabs skip an active claim. Completion and per-destination receipts match that token; explicit retries and expiry cleanup compare their read revision, including a missing revision on older records. A removed/recreated or newly claimed job cannot be deleted or overwritten by a stale send. Checkpoints renew the lease, and a bounded timer wakes recovery after an abandoned lease; a suspended tab can still have an already-dispatched request, so the lease is not a server exactly-once guarantee.

Resolved conversations, the uploaded media URL and confirmed conversation/story destinations are persisted under the claim. Recipient-resolution failure retains the unresolved recipients and fails before upload, rather than dropping a recipient or treating an empty result as success. Failed saved jobs restore with an explicit retry control. A retry uses the saved remaining destinations and uploaded URL; successful destinations are not deliberately sent again. DMs retain deterministic server message identities. An upload whose local checkpoint did not commit can leave orphaned bytes and need another upload.

Story dispatch is recorded before the request. If the acknowledgement is unknown, reconnect pauses the job with “Check your story before retrying to avoid a duplicate.” An expired story claim and pre-revision owned story rows also pause conservatively. Confirmed story checkpoints remove the destination. The message is fully visible in the progress panel, and only an explicit retry resumes uncertain story work.

Stories still use a client-authenticated direct insert without a trusted server receipt. A request may commit while its response or local acknowledgement is lost; an explicit retry can therefore duplicate a story. A fixed client document ID alone would not solve this safely: current story rules allow the owner to delete a story, so replay could recreate intentionally deleted content. Completing story idempotency requires a reviewed authenticated callable, immutable owner/request receipt and deletion/replay policy. This checkpoint intentionally does not change those backend/rules boundaries.

Focused tests cover sender/profile mismatch, account changes during lookup/upload/delivery, same-owner session restoration, cache key isolation, ownerless/foreign rows, concurrent queue instances and destination receipts, stale completions/revisions, storage failure, partial delivery across reload, unresolved recipients and uncertain story replay. The IndexedDB adapter tests verify use of the atomic primitive and failure propagation with a mocked adapter; queue concurrency tests use an injectable atomic memory store. They do not certify real IndexedDB durability across process crashes, native background suspension, camera permission or multi-device delivery. No real message, story, upload or external notification is created.
