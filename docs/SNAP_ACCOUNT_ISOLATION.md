# Snap sender account isolation

A background camera job captures its Firebase Auth UID and account epoch before it starts. Its upload path, verified sender profile, optimistic message key, confirmation, retry and progress display remain attached to that session. Changing accounts or logging out and back into the same account invalidates the old live job. A stale completion cannot populate the new account's message cache or start a later delivery stage. The editor stays open if its account changed before dispatch; the immediate camera toast describes preparation rather than claiming delivery.

Online jobs verify `profiles/{senderId}.user_id` through a fresh Firestore server read before resolving conversations or uploading media. Image compression, cover generation, conversation creation and story publication check the captured guard around their asynchronous boundaries. Stories use the verified original profile rather than resolving whichever profile is current later. The DM core receives the same guard and deterministic destination-specific message ID. Existing server authentication, membership and storage rules still authorize each request.

Offline queue records now have `schemaVersion: 2`, `ownerUid` and the original `senderId`. They retain the original draft, media, unresolved recipients and caption. Another account's queued records are skipped without changing their status or attempts; they do not block that account's later jobs. A restored job must match the active Auth UID and pass fresh profile-ownership verification before any upload or delivery. An old live job from a previous account epoch is not silently revived in the same page. A page reload can restore a recorded-owner job into a newly verified session for that same owner.

Older local queue entries lack trustworthy owner bindings. They remain unsent and are marked failed instead of adopting the current account or guessing that a profile ID is an Auth UID. There is no automatic migration of those media blobs. The user must deliberately recapture/resend an unverifiable draft. Failed expired cleanup only touches the current recorded owner's jobs. The queue remains local device storage; this does not add encryption or a multi-device draft service.

The DM transport also sends the captured `expectedSenderUid`. The updated `sendDmMessage` callable rejects a mismatch with its authenticated caller before rate-limit/database work, closing an account switch during SDK token selection. This requires a coordinated, selective callable/client rollout; client guards alone are not that server guarantee. Client guards cannot recall a request already dispatched with the original owner's authentication before an account change. Such a request may complete; its old job's completion is suppressed in newer sessions. Upload bytes already accepted are not deleted automatically. This pass does not add story idempotency, revoke existing media URLs, change membership rules or certify native background delivery. DM server idempotency preserves normal same-session retries; restored media may be uploaded again. Production/provider delivery was not exercised by these tests.

Focused tests cover sender/profile mismatch, auth restoration and account changes during lookup/upload/delivery, same-account logout/login, cache key isolation, ownerless and foreign queued records, valid same-account retries, compression/cover/story guards and bounded conversation-creation continuation. They mock transports and use local in-memory queue storage. No real message, story, upload or external notification is created.
