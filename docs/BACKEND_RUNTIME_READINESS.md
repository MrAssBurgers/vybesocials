# Backend runtime readiness

The complete read-only production inventory on 2026-10-06 at 19:36:17 UTC contained 233 functions, all ACTIVE on `nodejs20`. All pages were read. This proves the runtime inventory at that checkpoint; it does not prove every function works or that its dependencies are patched.

Google's [runtime support schedule](https://docs.cloud.google.com/functions/docs/runtime-support) lists Node 20 decommission on 2026-10-30. Node 22 is supported, with decommission scheduled for 2027-10-31. Migrating deployed functions to a supported runtime is an outstanding user-readiness requirement. No runtime migration is claimed by the location dependency release.

Use each function's current, versioned deployed archive as the starting point. The repository's whole Functions tree contains other unreleased handler changes and cannot be substituted for those archives. A runtime-only candidate must preserve compiled handlers, assets, dependency versions, entry point, trigger, environment and secret bindings, account identity, network policy, scaling, concurrency, memory and timeout. Capture the actual configuration and previous Cloud Run revision before deployment, and compare them afterward. Store sensitive configuration only in ignored local work files; published receipts should contain hashes and safe configuration summaries.

Test the candidate under the intended Node runtime, including actual handler loading, relevant authorization and behavior regressions, then deploy named reviewed targets. Verify ACTIVE status, the exact uploaded archive and runtime, retained configuration, and appropriate live boundaries. Empty unauthenticated probes can verify authentication rejection; they cannot certify signed-in behavior or real provider delivery. Event and scheduled functions need their own trigger and delivery checks.

The Firebase CLI can add deployment defaults even when handler source is unchanged. The location dependency rollout introduced a 20-instance limit absent from the previous revision. Verification caught it. Attempts to clear the field with an omitted or zero value left that limit in place; a separate, field-scoped operation explicitly restores the prior effective maximum of 100. Google documents [100 as the default revision maximum](https://docs.cloud.google.com/run/docs/configuring/max-instances). That changes the representation from unset to explicit while preserving the effective limit; the receipt must verify the actual outcome. Do not assume a source-only candidate implies configuration preservation. Recheck the actual configuration for every rollout.

Remaining readiness gates include other dependency advisories, first-factor/MFA authority review, physical Play Store package adoption and GPS/media performance, and legitimate preserved-content restoration. A runtime migration or an individual dependency patch does not close those gates.
