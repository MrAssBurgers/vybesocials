# Backend runtime readiness

The latest complete read-only production inventory on 2026-10-06 at 20:32:24 UTC contained 233 ACTIVE functions: 11 on `nodejs22` and 222 on `nodejs20`. All pages were read. Three core services were migrated earlier; eight social services are now verified on Node 22 with narrowly updated dependencies. See [the core migration receipt](../releases/node22-core-20261006/verification.json) and [the social canary receipt](../releases/node22-readiness-canary-20261006/verification.json). The other 225 function metadata rows match the pre-canary snapshot after canonicalizing object keys and unordered event-filter sets. The repository's default Functions engine remains Node 20 pending the remaining migration; do not use the unreleased root tree for a broad deployment. Inventory does not prove every function works or that its dependencies are patched.

Google's [runtime support schedule](https://docs.cloud.google.com/functions/docs/runtime-support) lists Node 20 decommission on 2026-10-30. Node 22 is supported, with decommission scheduled for 2027-10-31. Migrating deployed functions to a supported runtime is an outstanding user-readiness requirement. No runtime migration is claimed by the location dependency release.

Use each function's current, versioned deployed archive as the starting point. The repository's whole Functions tree contains other unreleased handler changes and cannot be substituted for those archives. A runtime-only candidate must preserve compiled handlers, assets, dependency versions, entry point, trigger, environment and secret bindings, account identity, network policy, scaling, concurrency, memory and timeout. Capture the actual configuration and previous Cloud Run revision before deployment, and compare them afterward. Store sensitive configuration only in ignored local work files; published receipts should contain hashes and safe configuration summaries.

Test the candidate under the intended Node runtime, including actual handler loading, relevant authorization and behavior regressions, then deploy named reviewed targets. Verify ACTIVE status, the exact uploaded archive and runtime, retained configuration, and appropriate live boundaries. Empty unauthenticated probes can verify authentication rejection; they cannot certify signed-in behavior or real provider delivery. Event and scheduled functions need their own trigger and delivery checks.

Deployment defaults can change even with a direct API request scoped only to runtime and source. Both the earlier CLI location release and six services in the social canary acquired a 20-instance limit absent from their previous revisions. All six canary corrections completed; each now explicitly retains the previous effective maximum of 100. Google documents [100 as the default revision maximum](https://docs.cloud.google.com/run/docs/configuring/max-instances). Previous revision metadata confirmed the limits were unset. This changes the representation from unset to explicit while preserving the effective limit; canonical effective settings match and all other settings remain unchanged. Attempts to clear the field with an omitted or zero value during the earlier location release left the lower limit in place. For remaining rollouts, inspect the previous revision and explicitly preserve its effective limit in the update, then recheck the actual configuration. Do not assume a source-only candidate implies configuration preservation.

Candidates change only the two engine/dependency manifests: Node 20 to 22, proxy-addr 2.0.7 to 2.0.8, and grpc-js 1.14.4 to 1.14.5 where needed. Other dependency entries and handlers are retained, including seven older-bundle dependencies that differ from the repository. Exact dependency installs used disabled install scripts; this does not verify native/media installer behavior. Only the eight named canary targets have been deployed from these candidates. Event and scheduled delivery and authenticated behavior remain separate checks.

Remaining readiness gates include other dependency advisories, first-factor/MFA authority review, physical Play Store package adoption and GPS/media performance, and legitimate preserved-content restoration. A runtime migration or an individual dependency patch does not close those gates.
