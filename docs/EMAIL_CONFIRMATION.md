# Email sign-in confirmation

The existing email confirmation flow now uses `auth2faRequest`, `auth2faVerify` and the email fallback in `authLoginApproval`. This repairs code issuance/verification; it does **not** establish server-enforced Firebase MFA. First-factor Firebase credentials still grant access to routes/rules that do not require a second-factor claim. Settings toggles, restored sessions, QR/device approvals and first-factor access need a separate coordinated authority migration before claiming MFA protection. Do not deploy this as a completed MFA rollout.

## Challenge authority

- OTPs use cryptographic randomness, six digits and a salted HMAC. Hash/salt/email/account creation proof live only in `_auth_email_challenges`; `_auth_email_limits` meters sends across a UID's challenges. Both namespaces deny all client access and carry a one-day `expireAt` TTL for eventual cleanup; expiry/status checks never wait for managed deletion. Public challenge rows contain status, channel and revision only. Rules reject legacy rows containing OTP hashes, token/session metadata, or email-2FA type regardless of their IDs.
- Creation requires authentication. Resend requires a valid existing challenge; an authenticated caller cannot overwrite another owner's challenge. Current Auth email, disabled state and account creation identity are checked. Caller-supplied email is never a destination. Existing legacy email challenges have no private proof and require a fresh sign-in. A pending device-approval challenge may deliberately switch to email.
- Five sends per UID per ten minutes, ten code attempts per challenge, ten-minute codes and a thirty-minute flow lifetime bound retries. Resend does not reset attempts or revive resolved challenges. A pending send has a short concurrency lease; late delivery cannot overwrite a newer revision, changed account, channel or denial.
- Provider acceptance requires a successful response containing an ID. Requests have a fifteen-second timeout and a per-delivery idempotency key. Acceptance means queued by the provider, not inbox delivery. Timeout/lost acceptance does not activate a code or claim sent; the user may request another code.
- Verification commits a single-use consumption transaction after minting a candidate token and rechecking current Auth and challenge state. Only the transaction winner receives its token. Codes and salts are removed on consumption. Tokens are not placed in readable challenge rows; no `profiles/{uid}` placeholder or untrusted verification flag is created. A lost final response requires a fresh sign-in, rather than replaying a consumed code. Firebase Auth reads/token creation and Firestore transactions are not one cross-service atomic operation.

## Client and rollout

The October 5 sign-in repair additionally waits for checked device registration before opening the app. Email completion carries its exact challenge ID; `authLoginNotify` verifies the Firebase `email_2fa` token claim against the current account and consumed private challenge, then returns `confirmedEmailChallengeId` only after the trusted device update and final recheck. A method string or a deferred new-account receipt is not confirmation. Checked profile setup occurs privately before device registration, and its result is reused after success. See [SIGN_IN_RECOVERY.md](SIGN_IN_RECOVERY.md) for the live mismatch and exact release dependencies.

Interactive checks have a 20-second deadline and an in-memory gate when browser storage fails. The modal awaits completion and prevents ordinary dismissal while busy. View/attempt guards reject late UI continuations; they do not cancel an already-dispatched Firebase custom-token exchange itself. Concurrent external account mutation during that SDK exchange remains a separate limitation. Browser reloads do not certify physical phone force-close persistence.

Password sign-in has one email gate, shared with interactive OAuth. Settings come from a current server read; failed reads, malformed flags, provider errors or incomplete/other-owner challenge receipts fail that client sign-in instead of silently skipping an enabled check. Attempts own their checking gate and bind the current UID/account epoch, including same-account supersession and A-to-B-to-A changes. Retired work cannot hydrate profiles, sign out a replacement account, end a newer gate, or clear its delayed native credential copy. The code modal requires a token/session receipt, retains partial drafts after resend failure, and ignores retired account/view results. Failed approval cancellation stays visible for Retry.

Keep `auth2faRequest` out of rollout until the broader authentication migration above is reviewed. When that migration is ready, `auth2faRequest`, `auth2faVerify`, the email branch of `authLoginApproval`, rules, the two private `expireAt` TTL policies and matching client must ship together. A stale `{ok:true}` endpoint without a challenge now produces a deliberate sign-in error, so publishing the client alone is not compatible for accounts with email confirmation enabled. No Auth configuration or secrets were changed by this repair.

## Verification

`scripts/test-email-challenges-backend.mjs` requires the isolated `demo-vybe-contacts-qa` Auth and Firestore emulators. It uses injected/intercepted mail/token providers; no real email is sent. Tests cover ownership, malformed/missing receipts, stale public secrets, attempt/send limits, resend/consume races, account/email/mode changes, expiry, provider failures and client rule denial.

`emailConfirmation.test.ts`, `LoginGateModal.test.tsx`, `authSessionAttempt.test.ts` and the mirror regressions cover incomplete receipts, missing tokens, provider errors, resend drafts, account changes, retired views, delayed cleanup, duplicate auto-submit and failed cancellation. The retained local preview uses an ignored, guarded sink only for `confirmation-qa@vybe.test`; that provider and its synthetic outbox are not production code or evidence of real email delivery.
