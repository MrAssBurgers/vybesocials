# Account profile setup and reviewed recovery

This checkpoint repairs existing signup, sign-in, onboarding and migrated-profile setup. It does not add an authentication provider or establish server-enforced MFA. No production deployment, Auth configuration change, secret change or real provider request is part of this work. Follow [DEPLOY.md](../DEPLOY.md) for the coordinated release; `auth2faRequest` remains excluded under the existing restriction.

## Ownership and compatibility

`ensureAccountProfile` is the authoritative callable. The existing `claimProfileByEmail` export now delegates to the same strict contract; its name no longer implies email-based claiming. Both require an authenticated caller, matching `expectedOwnerUid`, the current Firebase Auth account's creation time in `expectedAccountCreatedAt`, a UUID `requestId`, and an action (`ensure`, `syncIndex` or `recover`). They share a per-UID limit of 30 calls per minute.

- `ensure` preserves the exact ID and content of an existing uniquely owned profile, including a migrated profile whose document ID differs from its Firebase UID. A missing index can be repaired. Existing owners do not need an email or a verified email merely to load their profile.
- A new account with no conflicting identity receives its own UID-keyed profile, generated or validated requested username, and `onboarding_completed: false`. An unverified email account can create its own empty profile. Client preflight username availability is not ownership evidence or a guarantee that the name remains available.
- `syncIndex` requires `expectedProfileId` and confirms the same currently owned profile. It cannot link a foreign profile or invent an owner from an index.
- Duplicate ownership rows, a conflicting UID document, conflicting indexes/bindings, deleted profiles and profile-ID/Auth-UID collisions require review. The service does not pick the first candidate, delete a supposed placeholder or merge social data automatically.
- A public email match can stop duplicate creation and request review. Public email, display name, founder username and a mutable legacy index never authorize transfer or grant staff roles.

Successful receipts bind `ownerUid`, `accountCreatedAt`, `requestId`, `action`, `profileId`, a 48-hex `bindingRevision`, current owned `profile`, and boolean `created`/`recovered` fields. A replay must match its original payload and binding, then recheck current ownership. It does not resurrect a missing profile or return an old stored profile snapshot as current. Later profile edits are retained. Clients validate the receipt before hydrating a profile, updating their identity cache or reporting setup success.

The client retains unconfirmed requests in bounded same-tab storage using UID, Auth account creation time, action and expected profile ID. Network failures and invalid replies keep the original body for retry. A confirmed invalid-argument or already-exists rejection retires that attempt so a corrected setup can proceed. These local attempts are not authority. Account epoch, provider lifetime and operation guards reject A → B → A and replaced same-account continuations before later writes or cache effects. Profile scope uses one account observer consistently; separate observer counters must not be compared. Bootstrap (including its lazy import) and the direct service have a 15-second client deadline: timeout exposes retry and ignores late UI/cache results while retaining the request because the server may still complete it.

Firebase Auth account creation and profile setup are separate results. If Auth signup succeeds but profile setup fails, the account stays signed in with an explicit retry/recovery screen; the UI does not fabricate a persisted profile or ask the user to create the Auth account again. Initial disk snapshots do not unlock onboarding or account routes. A transient refresh may retain a profile already confirmed in the same session, but returns `null`; definitive ownership/permission failures clear it and expose setup recovery. Onboarding preserves the existing Skip policy. Normal completion waits for acknowledged avatar, private birthday, legal and profile saves, with completion written last.

## Reviewed legacy recovery

There is no automatic historical ownership proof in the repository's migration scripts. An exported source Auth record can contribute independent evidence only when its original source, integrity and relationship to the original profile have been reviewed. The current checkout does not include such an export. Copying current profile/index/email data into a private collection does not make it trustworthy.

The read-only helper `prepareAccountProfileRecovery` and `scripts/prepare-account-profile-recovery.mjs` prepare a candidate with `status: 'review-required'`. The script has no approve/apply option and does not change accounts, profiles or indexes. Its output contains account/profile identifiers and review metadata; handle it as private operator material. An operator must independently establish historical ownership before approving `_account_profile_recovery/{targetUid}`. Preparation alone is not approval, and approval alone does not silently move the user's account.

An approved version-1 record binds the target UID, current Auth creation time, hash of the current verified Auth email, exact source profile ID and owner UID, exact Firestore create/update timestamps, reviewer and review case. Recovery requires the user's explicit **Recover my profile** action. The current Auth account must still be enabled and verified, the evidence must still be approved, and the source profile must remain unchanged and not deleted. A changed snapshot requires a new review; do not overwrite the expected versions to force a retry through.

Both historical aliases—the source owner UID and source profile ID, deduplicated—must have no live Auth user. Only `auth/user-not-found` establishes absence; an Auth outage is an unavailable error. Any alias binding/index pointing elsewhere stops recovery. The transaction preserves the source profile ID, updates its owner UID, consumes the approval, writes the new active binding/index and durable receipt, and retires the old aliases. It removes only old alias indexes that point to this exact profile. It does not delete Auth users, other profiles, posts, DMs, roles or unrelated indexes.

Do not run `repair-all-user-data.mjs`, `repair-firestore-social.mjs`, `repair-everything.mjs`, `merge-founder-accounts.mjs`, or profile-derived Auth seeding as a recovery shortcut. Those historical scripts infer ownership from mutable data or perform broad and sometimes destructive changes. `verify-firestore-connections.mjs` checks connectivity, not provenance. `import-firebase.mjs` can import a separate source Auth export, but it does not generate reviewed recovery evidence. OAuth login does not by itself prove that a different Firebase UID owns a migrated profile.

## Rules, storage and limits

The new private collections are `_account_profile_bindings`, `_account_profile_recovery` and `_account_profile_receipts`; clients cannot read or write them. There are **no new composite indexes or TTL policies** for this checkpoint. Do not delete bindings, retired identities, approvals or receipts as cursor cleanup. Their retention needs an explicit operational policy; removing them can remove replay and retirement protection.

Direct client profile creation and `user_auth_index` writes are denied. Index reads remain restricted to the exact Auth UID. Ordinary owner profile edits remain available with immutable ownership fields and blocked public-email changes; setup no longer writes roles. Firestore `signedIn()` rejects retired/malformed bindings, and canonical profile checks verify current ownership. Empty unresolved profile IDs cannot authorize equality, staff-role or membership checks. Imported accounts can obtain their first checked binding without reassigning their profile.

Staff checks use the protected active binding's profile candidate after setup, then check the actual owner of a winning profile-alias grant. A UID-based grant is rejected when a direct profile at that UID belongs to someone else or is deleted. This prevents a legacy profile-ID role from being misread as an unrelated account's UID role. A separately granted `admin: true` custom claim remains its own authority, subject to the binding retirement check. Exact baseline comparisons identify two newly denied **unbound** legacy cases that work after checked setup: a migrated `user_roles_auth` UID `owner` staff read, and a migrated `user_roles_auth` UID `admin` role write. These are new setup prerequisites, not inherited failures to relabel as harmless. The four earlier migrated late-alias `user_roles_auth` admin/moderator read limits remain separate.

The shared `requireAdmin` helper also rejects retired/malformed bindings before checking custom claims or staff rows. Deploying only the setup endpoint does not update helpers compiled into other Functions. This dependency list is not permission to enable unused endpoints, configure providers, provision secrets or exercise AI/payment/email operations. `manageSecrets` remains intentionally unimplemented. Preserve existing secret bindings for reviewed deployed consumers; if a required consumer cannot be updated, retirement coverage is incomplete. Do not use a broad Functions deploy, and do not include `auth2faRequest`.

Important limits remain:

- Existing uniquely owned rows are preserved based on current canonical ownership, not retroactively certified against an immutable history. Earlier unauthorized or mistaken reassignment cannot be detected from present public data alone.
- Auth and Firestore cannot commit atomically. The service rechecks current Auth and old-alias absence immediately before transaction writes, and stores the current Auth creation time, but this is not a global Auth incarnation check for every token and every legacy callable.
- Firestore retirement and `requireAdmin` retirement do not automatically repair every legacy server path that uses only `requireAuth` or unchecked aliases. Those paths need a separate authority audit; do not claim universal old-token revocation from this checkpoint.
- A live, unbound Auth UID that collides with somebody else's legacy profile ID is rejected by checked setup and the repaired staff checks. Some older raw UID membership paths still do not independently resolve that collision. Preventing access through every such path needs a coordinated domain/rules migration; the profile gate alone is not a backend security boundary. Do not certify universal UID/profile collision protection from this checkpoint.
- Profile-ID-keyed social data remains reachable through the stable profile ID. Old UID-keyed data, provider links, roles, security settings and protected records with independently bound ownership may still need deliberate domain-specific recovery. This transaction is not a bulk data migration or a blanket entitlement transfer.
- Historical staff-read Rules budgets already have documented late-alias limits. Compare exact prior rules with current rules **after checked setup**, separately record unbound compatibility, and do not treat a newly denied previously supported role as an inherited limitation.

## Verification and release

The isolated fixture `scripts/test-account-profile-backend.mjs` covers Auth/Firestore ownership, collision, receipt, recovery and denial paths without production data. `scripts/test-account-profile-compat-rules.mjs` compares exact prior/current rules for staff read/write compatibility after checked binding. These must run alongside the affected existing authority suites before release. The client includes real `AuthProvider` regressions for StrictMode restoration, independently numbered account observers, delayed account switches, unmount, replaced refreshes, successful Auth signup with failed setup, explicit migrated recovery and transient versus definitive refresh failure. A hung setup times out without accepting its late result. Map tests retain existing alternate modes and verify 3D camera controls and explicit return from flat fallback.

Scoped evidence for this checkpoint: 18 backend groups, 34 account-profile Rules checks and 96 exact-baseline/unbound/bound compatibility comparisons passed in isolated emulators. The existing authority suite passed 115 checks plus four inherited-limit probes; profile visibility passed 71 checks, and the `requireAdmin` suite passed 26 unit tests. Functions build and scoped lint passed (two existing `auth.ts` warnings). The 13 real-`AuthProvider` regressions and 23 focused map checks passed; client typecheck and scoped lint passed. The release record must include the final integrated suite separately, along with the two setup prerequisites and remaining inherited limits above.

Review full rules, Functions and client from one tested commit. Arrange a controlled cutover: old clients that create profiles or write indexes directly are incompatible, and the old email-claim endpoint must not remain a transfer bypass. Deploy only the reviewed named endpoints and rules, then publish the matching client through **Lovable → Share → Publish**, subject to every other pending rollout prerequisite in [DEPLOY.md](../DEPLOY.md).
