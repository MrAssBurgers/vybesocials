# Email code reply recovery and phone animation work

An accepted email code was consumed before its HTTP reply reached the browser. If that reply was lost, repeating the code failed even though the person had entered it correctly. The deployed baseline reproduced this with an intentionally dropped committed response.

The verification screen now creates a cryptographically random 256-bit key for that attempt. The server stores only its hash when it consumes the code. The same mounted attempt can recover the response for ten minutes, after current account, email, creation, revocation cutoff and private/public proof checks. Different keys, wrong codes and expired or retired proofs cannot recover it. The original consumed time stays fixed; retries do not extend the completion window. Plaintext codes, keys and custom tokens are never written to the database. Legacy clients without a key remain one-use. The client keeps retry material only in the active view, clears it on retirement/resend/success, and offers Retry code check after a transport failure. Accepted-code completion remains separately retryable.

Phone sign-in/signup buttons keep their soft colors with still layers, releasing their animation hints. The existing light wave continues to acknowledge the operation. This reduces decorative work; it does not establish a physical-device frame-rate or instant network response.
